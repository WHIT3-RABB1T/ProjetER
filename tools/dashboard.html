🔒 Cryptography

What's actually protecting the link between the board and this server, and what it doesn't cover.

🤝 Transport: TLS 1.2, and only 1.2

Both the board's connection and this browser's are pinned to exactly TLSv1.2 -- ctx.minimum_version and ctx.maximum_version are set to the same value in tools/http_server.py. That's not a security preference so much as a hard constraint: the board's TLS stack (NetX Secure, via nx_secure_tls_api.h) only implements TLS 1.2 at all -- offering anything newer would just fail to negotiate with the one client that actually matters here.

🔑 Cipher suites -- two different clients, two different deals

The server offers four cipher suites on the same port, with the same certificate. Each client picks whichever one it can actually do; there's no separate "board port" and "browser port".

SuiteKey exchangeBulk cipherIntegrityUsed by
TLS_RSA_WITH_AES_128_CBC_SHA256 Static RSAAES-128-CBCHMAC-SHA256 board
TLS_RSA_WITH_AES_256_CBC_SHA256 Static RSAAES-256-CBCHMAC-SHA256 board
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 ECDHEAES-128-GCMAEAD (built in) browser
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384 ECDHEAES-256-GCMAEAD (built in) browser

The split exists because the board's crypto library implements no elliptic-curve or AEAD primitives at all (see nx_crypto_tls_ciphers in NetXDuo/App/nx_secure_user.h) -- static-RSA key exchange and AES-CBC are the only things it can do. Modern browsers, in turn, have deliberately stopped offering non-forward-secret suites like those for years -- a real Firefox connecting to a server offering only the board's two suites gets a flat refusal (SSL_ERROR_NO_CYPHER_OVERLAP) before any page ever loads, which is exactly what happened here until the two ECDHE suites were added alongside them.

🔁 How the board's own handshake actually works

1ClientHello -- the board proposes TLS 1.2 and its two supported cipher suites.
2ServerHello + Certificate -- this server picks one of those two suites and sends its self-signed RSA certificate.
3Certificate check -- the board compares the presented certificate byte-for-byte against the one copy it has embedded at compile time. No CA, no chain -- an exact match or nothing.
4ClientKeyExchange -- the board generates the pre-master secret itself and encrypts it directly with the server's RSA public key. This is the "static RSA" part, and the slow part: it's a 2048-bit modular exponentiation running entirely in software on the Cortex-M33, no hardware crypto offload wired up.
5Finished, both directions -- both sides derive the session keys from that pre-master secret and confirm the handshake transcript matches.
6Application data -- the JSON sensor reading goes out as one or more AES-CBC-encrypted, HMAC-SHA256-authenticated TLS records.

📜 The certificate, and what "trust" means here

tools/gen_https_cert.sh generates a self-signed 2048-bit RSA certificate (issuer == subject, CN=<board's LAN IP>) with a 10-year validity window -- chosen specifically because the board has no RTC or SNTP wired up, so it has no live clock to check a shorter window against anyway.

The board doesn't validate this certificate the way a browser validates a real one (checking a signature chain up to a trusted CA). Instead, tools/gen_https_cert.sh also bakes the exact DER bytes of this one certificate into NetXDuo/App/https_ca_cert.h, and the board's only check is: does the certificate the server just presented match those exact bytes? That's appropriate for a closed link between one known board and one known laptop on a private hotspot -- it would not be an appropriate trust model for anything reachable from the wider internet.

⚠️ Known limitations

  • No forward secrecy on the board's own connection. Static RSA key exchange means if the server's private key were ever compromised, every past captured session from the board could be decrypted retroactively. (The browser's ECDHE connection doesn't have this weakness.)
  • Certificate pinning, not real CA validation. "Trusted" means "byte-identical to the one copy the board was built with" -- there's no revocation, no chain, no way to rotate the cert without reflashing the board.
  • RSA runs entirely in software. This was a real, reproduced problem this session: building the board's firmware at -O0 (STM32CubeIDE's Debug default) could make individual handshakes take 20+ seconds, occasionally long enough to look like a hang. Fixed by building at -Os instead -- see the project history for the full diagnosis.
  • TLS 1.2 only. No 1.3, because the board's NetX Secure stack doesn't implement it.
